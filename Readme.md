hi。不好意思是我关于充电cost的结果算错了，才导致结果比之前进步了。

接下来我介绍一下我目前的思路和进展。

我认为在GB-ACO算法中可以把优化流程分为三个层级，由大到小依次是：
    1. cluster 层级（将所有客户划分为若干个簇，每个簇对应一条完整路径）
    2. GB 层级 （每个 cluster 被进一步划分为若干个 GB）
    3. customer 层级 （每个 GB 中包含若干客户节点）

在现有流程中，每个 cluster 对应一条路径；cluster划分为多个GB，通过 ACO 规划 GB 之间的顺序，并在每个 GB 内分别运行 ACO 得到 GB 内的最优路径，最后将这些 GB 内的路径拼接起来，形成 cluster 的完整路径。

## 最近做的事情：
我发现现有方法存在一个关键问题：虽然每个 GB 内部路径是最优的，但 GB 之间的连接方式不一定最优。
例如：GB1 最后一个节点 和 GB2 第一个节点 的衔接cost可能很大，但 ACO 没有全局考虑。换句话说，从 GB 的层级（第2层）来看，最终路径可能只是局部最优，并不是全局最优路径。
于是，我尝试在 GB层级 引入局部搜索策略
    1. 从拼接后的 GB 路径中移除部分客户（跨 GB remove）;
    2. 然后采用贪心策略重新插入（跨 GB reinsert）到最优位置。
也就是在这里，我算错了充电cost的结果，导致我认为结果提升了很多。昨天我修正完代码后发现 实际上结果提升并不明显!

## 接下来要做的事情：
目前，从 GB 的层级（第2层）来看已经是最优了，但是如果层级再放大一些，从cluster层级 （第1层） 来看，结果仍然可能只是局部最优，这也是目前的瓶颈所在。
如rc201的结果图所示，在当前的聚类结果的前提下，这个路径结果已经较为紧凑（路径没有冗余，绕路）。但是整体 total cost仍然比对照算法TSHACA大，这是为什么？

我认为原因是：
    Cluster 的划分固定了每条路经中的customer节点，每条路径中的客户无法跨 cluster 调整；这限制了整体调度方案的优化空间，可能是当前成本高于对照算法 TSHACA 的主要原因。

为此，我计划在 Cluster 层级 引入局部搜索策略：
    1. 在所有路径中移除一部分客户（跨 cluster remove）；
    2. 然后基于贪心策略在全局范围内重新插入到合适路径中（跨 cluster reinsert）。
通过这种方式，打破 cluster 的固有结构。
